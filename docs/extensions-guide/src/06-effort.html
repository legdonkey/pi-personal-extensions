原位思考强度：按消息选档位

按每条新用户消息调整 GPT-6 Codex、Anthropic 协议分支的指定 Claude 模型或 Antigravity 分支的指定 Claude 模型的思考档位。三个分支分别用 configuration_update、Anthropic 原生逐消息标记或插件 runtime ID 路由写入档位。用户提交时后台分类，发请求时最多再等 5 秒；检测到两次缓存重建会暂停自动调整；菜单里还能运行判档测评。

功能 ID
inline-effort
入口
/personal → 原位思考强度
配置
默认 ~/.pi/agent/inline-effort.json，目录跟随 PI_CODING_AGENT_DIR；兼容读取旧的 jev-inline-effort.json

Jev（默认）· d1-ultra · Mammoth 27B · Decider v1.2

什么时候分类

不同的消息需要的思考强度不同。这项功能给每条新用户消息自动选一个档位，结果叫决策。档位是思考强度的取值，分类器从 low、medium、high、xhigh、max 五档里选。 GPT-6 Codex、Anthropic 协议分支的四个指定 Claude 模型，或 Antigravity 分支的两个指定 Claude 模型才适用，thinking 不能是 off。Anthropic 协议分支还要求接口是 anthropic-messages，compat.supportsMidConvoEffort 为 true。Antigravity 分支要求 provider 是 antigravity，接口是 antigravity-api。不适用就不分类。 分类规则按主模型分两套。按模型规则覆盖五个模型：先是共用的原则，再接该模型的说明和五档条件。共用原则按工作阶段、隐藏边界情况的密度和自主执行的长度判断，还参考当前强度识别进展信号；首句是「为当前主会话的下一轮选择推理强度」，不再写 Claude Code。 Opus 5.5、Sonnet 5.5 和 Fable 5.2 的规则移植自 Claude Code 的 auto-effort mod 里的 policy-text，依据是 Anthropic 官方的 effort 与 prompting 指南。GPT-6 Astra 和 GPT-6.1 Sol 的规则依据 OpenAI 官方的模型指南、Reasoning models、Model selection 和 Codex 文档整理，两者的默认档都是 low。 Opus 5 和其他 GPT-6 Codex 模型仍用通用规则，按推理结构切分：low 直接执行明确操作，medium 做局部判断，high 综合多项约束，xhigh 处理冲突证据与耦合推理，max 仅作例外攻坚。 通用规则下，近期对话只补全同一任务的信息，不继承旧难度。示例：修改位置和方式明确的字号调整可用 low，改做图示设计可用 high；按成熟口径查数画图可用 medium，排查混杂原因可用 xhigh。示例不是线上分类保证。 通用规则不因专业主题、成片精美、代理多或反复报错自动提档；只有无法识别任务要求时才以 high 保守兜底。思考强度不替代模型专长、授权和实测。两套规则下，分类器都只读有限文本，看不到图片和工具结果，同轮工具续调不重新分类，历史决策不变。 空白输入不调用分类器，沿用当前强度。当前强度是当前分支最近一次决策；没有决策就用基线，也就是 Pi 的 thinking 设置。 非空才分类。用户提交消息时，扩展在 input 事件里就开始后台分类；发请求前最多再等 5 秒。超过 5 秒就沿用当前强度，中止分类并丢弃迟到结果，每个会话只在第一次超时时提醒。 发请求时，扩展按最终上下文重新生成分类文本。和后台任务一致就直接复用结果；输入经过模板展开或近期对话变了，就丢弃旧任务重新分类。后台每个分类模型仍限时 15 秒，首选非 Jev 模型超时或报错后尝试一次 Jev。

分类结果怎么用

分类正常完成、档位有效，且概率是 0.5 到 1 之间的有限数，这叫结果合格。结果合格，扩展就采用这个档位。 首选非 Jev 模型超时或服务出错时，警告先显示安全原因和「正在切换到」提示，再尝试一次 Jev。Jev 成功就采用新档位；仍无合格结果则沿用当前强度。结果无效或有效结果的概率低于 0.5 时均不触发回退，直接沿用当前强度：结果无效发一次警告，低置信度静默沿用。直接选择 Jev 时不反向回退。 采用、最终沿用和等待超时都写入决策。回退成功时记录实际分类器和回退来源；等待超时不记分类器；用户取消时不回退、不写入。 多条新消息只分类一次，结果写给每一条。

Codex：为什么不改顶层参数

对 GPT-6 Codex，Pi 每次请求前，都按当前上下文构造完整的 input 列表。基线写在请求顶层的 reasoning.effort 字段。 新请求开头里和上一次请求相同的部分，叫缓存前缀。服务端复用缓存前缀的机制叫 prompt cache。README 的设计目标是保留缓存前缀，让 prompt cache 生效。 如果直接改 Codex 顶层，请求 2 从顶层字段起就和请求 1 不同。Pi 的 WebSocket 增量续传也要求 input 和 previous_response_id 以外的字段不变，否则发送完整 input。

按接入分支写入档位

对 GPT-6 Codex，扩展让顶层保持基线，在当前用户消息前插入一个 configuration_update 项，只写新档位。档位写在 input 里这条消息的位置上，这就是「原位」。 决策按消息时间戳存在会话里。模型、基线和已有上下文不变时，下一次请求重放同样档位，开头逐项不变。 Codex 档位和当前强度相同时，扩展不插入。档位回到基线时，扩展也要插入一项，抵消之前那一项。 Anthropic 协议分支使用 Pi 原生标记。扩展只修改 Pi 已生成的末尾空 system 消息里的 output_config.effort。顶层 output_config、thinking 和历史消息不变。message_end 保存实际发送的 providerThinkingLevel，供 Pi 重放历史标记。主会话 thinking 基线不变。 同一 Anthropic 协议请求由提供方内部重建或重试时，扩展复用原模型快照。流式期间切换模型后，旧回复仍保存实际档位。扩展不干预 Pi 的 max_tokens: 1 缓存预热回放。当前没有请求 ID 可用于区分请求，因此 max_tokens: 1 的主请求也不自动调整；等待 Pi 暴露请求 ID 后再区分。 Antigravity 是独立分支，不使用 Anthropic 消息级 output_config。插件不触发 onPayload，所以扩展在 context_with_system 分类后临时包装原生 streamSimple。扩展只改匹配当前 session、末条消息 timestamp 和模型的主请求 options.reasoning，交给插件按 -low、-medium、-high runtime ID 路由。max 和 xhigh 夹到 high，会话 thinking 和历史上下文不变。 Antigravity 的 message_end 保存实际 providerThinkingLevel。工具续调、重试和恢复沿用原决策。maxTokens: 1 预热和辅助 session 不干预。退出只恢复原 streamSimple，保留第三方后来的部分更新，也不覆盖第三方替换的新流。 Fable 5.2 只走 Anthropic 协议分支，依据是 Pi 1.5.2 模型目录声明支持逐消息 effort，序列化后仍是 adaptive thinking 加末尾空 system 标记。本次没有 Anthropic 认证，两轮真实请求的缓存读取还没验证。Antigravity 分支不加 Fable。

决策跟随会话分支

决策是会话里的自定义条目，不发给模型。扩展只读当前分支路径上的决策，所以恢复会话、fork 或树导航后，旧消息保持原档位，不重新分类。 从 A1 另开分支 b 时，扩展仍继承共同祖先 U1 的决策，但读不到分叉后 U2 的决策。U3 是新消息，重新分类。 压缩后，压缩摘要承接被压缩部分的最后一次决策，强度不回落到基线。

状态栏

状态栏的 🧠 段显示当前强度、基线和最近一次决策的分类器，例如 🧠 xhigh · 基线 medium · Jev。当前强度等于基线时，只显示一个档位。 非 Jev 模型回退成功时，分类器标注回退来源，例如「Jev（d1-ultra 回退）」或「Jev（Mammoth 27B 回退）」。全部失败时显示的是首选模型，表示最近尝试，不表示分类成功。 对 Codex，插入前，扩展核对 input 里 role 为 user 的项数。项数和本次上下文不一致时，扩展不插入，状态栏显示「未调整」。 缓存守护暂停后，🧠 段改为「🧠 自动调整暂停：检测到两次缓存重建 · /personal → 原位思考强度 → 恢复自动调整」，直到恢复或开始新会话。

缓存守护：两次重建就暂停

缓存守护读取主会话助手回复里的缓存读取量 cacheRead。只有本次请求调整过档位，而且上一次读取大于 0 时才检查。 三种正常失效直接跳过：两次主请求的开始时刻相隔超过缓存保留时间；上一次判断以来发生过压缩或树导航；请求模型变了。保留时间取 Pi 模型目录的 promptCache.short，Pi 1.5.2 的 Anthropic 模型是 300 秒；目录没有这个值时按 5 分钟。 剩下的情况里，这次读取少于上一次，就提示「检测到缓存重建」，写明两次读取量和可能原因。只是写入变大不算：Pi 把缓存断点放在最后一条用户消息上，一次读入很长的工具结果会让写入很大，但读取不会变少。每个用户轮次最多计一次，同一会话累计两次后暂停自动调整。 暂停期间不再调用分类器，新消息沿用当前强度。暂停和计数只存在扩展内存里：切换主模型不解除，新会话清零；也可以选「恢复自动调整」，立即恢复并清零计数。 这仍是异常信号，不是因果证明：服务端提前清除缓存，或其他扩展改了系统提示词或工具，也会让读取变少。

在 /personal 里管理

在 /personal 里选原位思考强度，再选「查看分类模型与状态」。它显示四项：是否适用、后续用哪个分类器、失败回退策略、当前分支最近一次决策。 通过「选择分类模型」打开选择器，选择后保存到全局配置，从下一条未分类的消息生效。其他会话和子代理的后续分类也读取这份配置。 「测试分类模型可用性」用固定样例测试首选模型和回退流程，明确显示实际成功的模型，不写决策。Pi 运行 agent 时，选择、测试和测评都不可用。 「恢复自动调整」只在当前会话因缓存重建暂停时有效，恢复后清零计数；没有暂停时只提示未暂停。 「运行判档测评」只在空闲的 Pi 终端界面可用，确认会消耗 OpenRouter 额度后才开始，按 Esc 键取消。 功能 ID 从 jev-inline-effort 改为 inline-effort。旧的开关和配置文件仍能读取，保存时只写新文件；会话里的决策条目沿用旧类型名，旧会话可以直接恢复。

判档测评

判档测评有 75 个用例，分别按 Opus 5.5、Sonnet 5.5 和 Fable 5.2 的规则各判一遍，共 225 次分类。它用当前分类器和运行时相同的回退规则，只调用分类器，不调用主模型。 结果显示全部和 holdout 的命中率、偏低、偏高、无效数和中位耗时。明细写到 agent 目录下的 inline-effort-bench 文件夹，只有用例 ID、档位、分类器、回退原因和耗时，不含消息原文。 测评期间，首选的非 Jev 分类器失败时不逐条弹出回退警告。结束时的汇总写明回退到 Jev 的次数和按原因的分布，明细每条也记录回退原因。正常对话中的回退提示不变。 用例原样复制自 auto-effort 的按模型标注版本，原始用例来自 HeyCubit 的 effortless，使用 MIT 许可，许可全文随扩展附带。其中 20 个 holdout 用例不用于调整提示词。 2026 年 11 月 14 日用 Jev 实测一次：按 Opus 5.5 的规则命中 74 个，Sonnet 5.5 命中 65 个，Fable 5.2 命中 70 个；中位耗时约 0.4 秒，225 次调用约 0.015 美元。命中率只说明分类结果和标注一致，不代表主模型完成任务的质量。

子代理与代价

子代理要加载本扩展才会分类，基线取子代理自己的 thinking 设置。外部 CLI 代理不经过本扩展。 代价有三项：提交时后台分类，发请求时最多再等 5 秒；分类、回退和判档测评消耗 OpenRouter 的额度；发出的文本可能含业务信息。四个分类模型均按输入计费。
