总览：Pi 屏幕上的六项功能

六项功能各改 Pi 屏幕的哪一块，由哪一章讲。

入口文件
extensions/pi-personal-extensions.ts
管理命令
/personal
开关文件
personal-extensions.json，默认在 ~/.pi/agent/，可用 PI_CODING_AGENT_DIR 改目录

pi-personal-extensions 是一个 Pi 扩展合集，共六项功能。后文单说「扩展」，指正在讲的那项功能的代码。 入口是 Pi 加载的那个文件。入口按 personal-extensions.json 里的开关加载六项功能，还注册 /personal 命令，用来启停和设置。

  • 消息区有两项：用户消息橙色线框，和文件路径可点击。
  • 状态栏由一项功能负责：它把额度和会话 ID 写进扩展状态行，还给 pi-statusline 那一行换配色。
  • 输入框下方的会话名由右下角会话标题显示；自动会话命名在一轮正常结束后，用命名模型在后台起名。
  • 状态栏里的 🧠 段来自原位思考强度。它支持 GPT-6 Codex、Anthropic 协议分支的三个指定 Claude 模型和 Antigravity 分支的两个指定 Claude 模型，为新用户消息选择思考强度。

六项功能默认全部开启，每一项都能单独关闭。

统一入口：按开关加载，一个菜单管理

入口怎样按开关加载功能，二级菜单怎样调用各功能的命令处理器，启停怎样保存并重载。

源码
extensions/pi-personal-extensions.ts
命令
/personal、/personal switches
配置
personal-extensions.json（agent 目录，默认 ~/.pi/agent/）
测试
tests/personal.test.mjs

加载：只注册开启的功能

Pi 加载入口时，入口先读 agent 目录下的 personal-extensions.json。agent 目录默认是 ~/.pi/agent/。 如果文件不存在，六项全开。如果文件不是 JSON 对象，或某个开关不是布尔值，入口抛出错误。 接着入口遍历 features，只对开启的功能调用 register。

  • 设置 PI_CODING_AGENT_DIR 后，agent 目录改用该变量指定的目录。
  • 多出的键（例如已移除的 terminal-title）被忽略；加载时不改写文件。
  • 旧开关自动映射：substatusline 和 statusline-style-picker 合成 statusline，两个都为 false 才关闭；jev-inline-effort 映射到 inline-effort。新键存在时以新键为准；下次保存只写六个新键。
  • 文件无法读取或 JSON 解析失败，同样抛错。抛错发生在注册之前，这次加载什么都不注册，包括 /personal。

featureApi：把命令收进内部表

register 收到的是 featureApi，它的原型是 pi。 调用 on 方法时，featureApi 自身没有，就落到 pi 上。 registerCommand 被截住：处理器只存进 commands 表，不交给 pi 注册。 所以 Pi 里只有 /personal 一个命令，各功能的处理器只能从它的二级菜单调用。

源码：featureApi 的定义 
// Object.create(pi)：新对象的原型是 pi
const featureApi = Object.assign(Object.create(pi), {
  registerCommand(name, command) {
    commands.set(name, command); // 只进内部表，不向 Pi 注册
  },
});

菜单：一级选功能，二级选操作

/personal 的一级菜单列出六项功能和加载状态，最后一行是「批量功能开关」。 如果选中已加载的功能，二级菜单列出 actions 表里的设置项，最后一项是「禁用此功能并重载」。 如果选中未加载的功能，二级菜单只有一项：「启用此功能并重载」。三级菜单按 Esc 返回二级，二级返回一级，一级才退出。保存设置或查看状态后留在二级菜单；需要重载时退出。

  • 只有四项功能有设置项：自动会话命名 6 项、原位思考强度 3 项、文件路径可点击 10 项、状态栏 1 项（选择 pi-statusline 自定义配色）。其余两项的二级菜单只有启停。
  • 「已加载 / 未加载」表示功能是否注册。功能自身的状态，用「查看状态」这类设置项确认。启停不清除功能自己的配置文件。

启停：先写临时文件，再 rename，最后重载

用户确认启停后，入口先比较新旧开关。没有变化就直接返回。 有变化时，入口先把新开关写进临时文件。 然后入口用 rename 把临时文件换成正式配置。同目录的 rename 是原子操作。 写临时文件或 rename 失败时，入口提示保存失败，功能保持不变。 保存成功后，入口调用 ctx.reload()。Pi 重载后，入口按新开关重新注册功能。

  • 临时文件名是正式文件名加随机 UUID 和 .tmp；权限 0600，只有文件所有者能读写；用 wx 标志创建，同名文件已存在时报错，不覆盖。
  • 失败时不重载。重载只作用于当前会话，其他已打开的会话需要各自执行 /reload。
  • 原子性来自 POSIX rename：读取方只会看到完整的旧文件或新文件。临时文件和正式文件在同一目录。

使用限制与批量开关

/personal 只要有交互界面就能用：TUI 和 RPC 客户端都行。没有界面时，入口只发一条提示。 「批量功能开关」只在 TUI 里可用：/personal switches 打开它，按空格切换一项，按 Enter 键保存并重载，按 Esc 键放弃。

  • 没有界面指 Print 和 JSON 模式。RPC 客户端里选「批量功能开关」时，入口提示改用各功能二级菜单里的「启用此功能并重载」或「禁用此功能并重载」。
  • /personal 只接受两种用法：不带参数，或带 switches。带其他参数时，提示「用法：/personal 或 /personal switches」。
  • 一级菜单的「批量功能开关」效果相同，保存走同一段写入代码。按键是 README 写的默认键位，确认键跟随 Pi 的 tui.select.confirm。

消息区：路径链接和橙色线框

两项功能都改消息的显示：一项在渲染前把文件路径改写成链接，一项在渲染后给用户消息加边框。

功能
文件路径可点击 clickable-paths；用户消息橙色线框 user-message-border
设置入口
/personal → 文件路径可点击（用户消息橙色线框只有启用 / 禁用）
配置文件
agent 目录下的 clickable-paths.json（默认 ~/.pi/agent/，跟随 PI_CODING_AGENT_DIR）

Pi 默认把消息里的文件路径显示成普通文字。文件路径可点击把路径变成链接，用户消息橙色线框给用户消息加一圈边框。 文件路径可点击在 Markdown 渲染之前改写文本。用户消息和助手消息默认都经过这一步。 用户消息橙色线框在渲染之后工作：它包装用户消息组件的 render，给输出的行加边框。

文件路径可点击 clickable-paths

扩展找两类候选：反引号里的行内代码，和带扩展名的裸路径。裸路径指正文里没加反引号的路径。 文件真实存在时，路径才变成链接。示例里的 node.js 不是文件，保持原样。

  • 裸路径的识别可以关闭：/personal → 文件路径可点击 →「不识别裸路径」。
  • 扩展缓存「文件是否存在」的结果，有效期 5 秒。缓存最多 4000 条；达到上限后，下次写入前清空整个缓存。有效期内删掉的文件，链接可能暂时还在。

跟着第一个候选往下看。扩展拆出末尾的行号和列号，再按会话工作目录解析相对路径。 扩展按设置的编辑器拼出 URL。默认编辑器是 vscode，URL 带上行号和列号。 最后，扩展把文本改写成 Markdown 链接。终端支持超链接时，Pi 输出 OSC 8 超链接：屏幕上只显示文字，点击文字打开背后的 URL。

  • 扩展按 / 把路径分段，逐段做 URL 编码。空格等字符会转义。
  • 带 :行 的路径找不到文件时，扩展把整串当文件名再试一次（文件名本身带冒号的情况）。这时链接不带行号。

哪些文本不改写

匹配到的反引号或波浪线围栏代码块里，路径不改写。四空格缩进的代码块不算围栏，里面的路径照常改写。 正则能识别的行内链接和图片原样保留。扩展仍可能改写引用式链接里的方括号文本。 扩展也不改写流式输出中的消息和思考块。流式输出中的消息等最终渲染时再处理。

设置和打开方式

设置有四项：总开关、编辑器、是否识别裸路径、是否处理用户消息。前三项在 /personal 的「文件路径可点击」二级菜单里改，第四项只能改配置文件。 编辑器选 file 时，扩展生成 file 协议的 URL，交给系统默认程序打开，不带行号。

  • 字段与默认值：enabled: true、editor: "vscode"、bareText: true、userMessages: true。
  • 菜单项调用功能内部的 clickable-paths 处理函数。这个函数只登记在 /personal 的命令表里，不注册成斜杠命令。

用户消息橙色线框 user-message-border

Pi 没有给普通用户消息提供边框钩子，所以扩展替换 UserMessageComponent 原型上的 render。源码注释写明这是临时方案。 会话关闭时，如果 render 还是线框这一层，扩展就把它改回原始方法。 如果后来别的 Pi 扩展又包装了一层，扩展不动它，只把线框这一层改成直接转发。

  • 只在 TUI 模式生效，给普通用户消息加橙色圆角边框。
  • 边框颜色 rgb(217,154,82)；边框字符的背景用主题的 userMessageBg。
  • 改的是原型，对所有用户消息实例生效；session_start 重复触发时，包装不叠加。

每次渲染的三步

第一步，按宽度减 2 调用原始渲染，给竖线留出两列。 第二步，把首末空白行换成上下边框。 第三步，中间每行两侧加竖线。边框不加行，但长行可能多折一行。 宽度小于 8 或行结构检查不通过时，改用原始渲染，不画边框。

  • 退回原始渲染时，功能仍是「已加载」状态。升级 Pi 后先运行 npm run check。

额度：什么时候刷新

想在状态栏看到服务商还剩多少额度，可以开启「状态栏：额度、会话 ID 与配色」。它在状态栏写会话 ID 的末尾 8 位和服务商剩余额度，也提供 11 套配色。 会话开始、树导航、切换模型时，扩展立即刷新额度。会话开始或树导航后，定时器每 5 分钟再刷新一次。 agent 一轮运行结束时，扩展也刷新额度。如果距上次刷新开始少于 30 秒，扩展跳过这次刷新。

  • 会话 ID 只显示末尾 8 位。Pi 默认用 UUIDv7 生成会话 ID，开头是时间戳，相近时间新建的会话开头相同，所以扩展取末尾。
  • 切换模型时，扩展取消还没完成的请求。会话关闭时，扩展停止定时器、取消请求，并清空两项状态。
  • 这一项由旧版的 substatusline 和 statusline-style-picker 合并而来，只有一个开关 statusline。配置里没有新开关时，由两个旧开关推出：两个都明确为 false 才关闭，否则开启。下次保存开关时只写新键。

一次刷新做什么

一次刷新分三步。第一步，扩展读取当前模型所属服务商的凭据。Antigravity 从当前 provider 获取 JSON 凭据，其他服务商调用 pi auth。 第二步，扩展带凭据请求服务商的用量接口。前三个服务商读取凭据和请求接口各有 15 秒超时。Antigravity 使用固定官方 endpoint 回退，总网络超时 15 秒。 第三步，扩展挑出额度窗口或当前模型配额，显示剩余百分比。额度窗口是按时间段统计的限额。openai-codex 显示周额度，zai-coding-cn 显示 5 小时和周额度，kimi-coding 显示 5 小时额度，老套餐附周额度，新套餐附月度额度。antigravity 显示 quota 60% left 这样的当前模型配额。这个配额可能使用共享池，不是独立的 5 小时或周窗口，也不是 token 计数。 请求失败时，其他服务商保留上次成功的值。Antigravity 找不到当前模型配额或查询失败时隐藏旧值。从没成功过时，额度一项为空。

  • 当前模型来自其他服务商时，额度一项为空。Antigravity 额度需要先安装并启用 pi-antigravity。
  • Codex、智谱和 Kimi 的剩余百分比 = 100 − 已用百分比，限制在 0～100，四舍五入。Antigravity 只接受有限数值 remainingFraction，约束到 0～1，再乘 100 并四舍五入；多个同模型变体取最低值。
  • Antigravity 按当前模型精确 ID 匹配，也匹配去掉 -extra-low、-extra-high、-minimal、-medium、-high、-low、-thinking、-tiered 后缀的运行变体。gemini-3.1-pro 还匹配 gemini-pro-agent，gemini-3.5-flash 还匹配 gemini-3-flash-agent。
  • Antigravity 每次刷新重新解析当前账号凭据。账号变化在下一刷新生效，扩展不主动监听账号切换。切换模型会强制查询，不显示旧模型缓存。

换配色

在 /personal 的「状态栏：额度、会话 ID 与配色」里，选择 pi-statusline 自定义配色。需要另外安装并启用 pi-statusline，不改变 Pi 主题。 终端里上下键实时预览，Enter 应用，Esc 取消；RPC 客户端使用普通列表。应用后覆盖自定义配色，并设置紧凑布局和圆角分隔符。

11 套配色怎么分组

每行是一套配色。每套有 6 组颜色，每组是一对前景色和背景色。 状态栏的 13 个字段按表头分成 6 组，同组字段共用一组颜色。 终端宽度小于 68 列时，预览拆成两行。每行都按终端宽度截断。

应用配色时写什么

应用配色时，扩展先读出原来的 pi-statusline.json。 扩展整体替换四个字段：配色预设、配色、密度和分隔符。其他顶层字段保留。 写入方式和第 2 章的启停相同：临时文件加 rename，成功后重载，失败不重载。

  • 文件位置：agent 目录下的 pi-statusline.json，和 pi-statusline 读取的位置相同。agent 目录默认是 ~/.pi/agent/，设置了 PI_CODING_AGENT_DIR 时用这个变量指定的目录。
  • 文件不存在时，扩展从空对象开始写；读取出错或不是合法 JSON 时，算作失败。

会话名：显示与自动起名

会话名怎么显示在输入框下方；自动会话命名怎么在后台起名、校验结果，并保护手动起的名字。

功能
右下角会话标题 session-title（显示）；自动会话命名 auto-session-name（起名）
入口
/personal → 自动会话命名（二级菜单）；本包只注册 /personal 一个斜杠命令
全局配置
agent 目录下的 auto-session-name.json（agent 目录默认 ~/.pi/agent，可用 PI_CODING_AGENT_DIR 改）

显示：右下角会话标题

会话多了以后，要靠会话名找回会话。右下角会话标题负责显示会话名，自动会话命名负责起名。 右下角会话标题只在 TUI 模式工作。它在输入框下方添加一个 widget。widget 是扩展自定义的一块界面。这个 widget 用一行暗色小字靠右显示会话名。 会话开始或会话信息变化时，扩展重画这一行；会话关闭时，扩展移除这一行。

清洗与排版

会话名可能带控制字符。扩展先删终端转义序列，再把换行、制表符等控制字符换成空格。 如果清洗后的会话名为空，扩展显示「未命名会话」。这一步只读会话名，不调用模型。

  • 换成空格的范围：\x00-\x1f、\x7f-\x9f、U+2028、U+2029；最后去首尾空白。
  • 颜色取主题的 dim 色，切换主题后跟着变。

起名：什么时候触发

自动会话命名在后台给会话起名，只在 TUI 和 RPC 模式下工作。 Pi 发出 agent_settled 事件后，扩展检查当前分支的最后一条消息。只有它是正常结束的助手消息，扩展才继续。

  • 「正常结束」指 stopReason 为 stop；还要求 Pi 空闲、on/off 状态为开启、会话名归本扩展。
  • Print / JSON 模式没有 UI，扩展直接返回；/personal 在没有 UI 时也只提示并返回。
  • 连续失败只提醒一次；配置、模型或档位出错时显示具体错误。

发给命名模型的上下文

扩展只读当前分支，从末尾往前数到第 5 条用户消息。 每轮只取文本：用户消息保留前 2000 个字符，助手回复保留最后 1500 个字符。 扩展不发送工具结果、思考块、工具调用和图片，也跳过出错或中断的回复。

  • 「字符」按 UTF-16 代码单元算。助手消息逐条拼接，每拼一条就去首尾空白、保留最后 1500 个字符。
  • 自动命名遇到进行中的请求会跳过；菜单里的「预览建议标题」会取消旧请求并重新请求。

标题格式与校验

命名规则写在系统提示词里。对话 JSON 作为用户消息发送，提示词要求模型只把它当数据。

提示词要求模型只返回含 title 字段的 JSON。title 为 null 表示当前会话名已准确或信息不足，扩展不改名。

  • 返回不是 JSON、多出字段、stopReason 不是 stop，都按失败处理。

试一试：标题校验

演示把输入的候选标题包成 {"title": …}，交给和源码相同的校验函数 parseSessionTitle。预设按钮覆盖常见的拒绝原因。

保护手动起的名字

扩展只改两种会话名：空的，或者等于它上次起的。 用户用 /name 改名后，扩展暂停这个会话的自动命名。 会话开始时，扩展先恢复保存的 on/off 状态；会话名不是它起的，也暂停。 在 /personal → 自动会话命名 里选「恢复当前会话命名」，扩展接管当前会话名，下一轮结束后生效。

命名模型与思考强度

命名模型默认是 gpt-5.6-luna，只从已认证的 scoped-models 里找。找不到时，扩展报错并保留原名，不回退到其他模型。 命名请求的思考强度默认继承 Pi 的逐模型设置，未配置时用 low。主模型和主会话的思考强度不变。

  • 配置文件不存在时用默认值；文件损坏时报错，不调用模型，也不覆盖文件。保存时先写临时文件，再用 rename 替换，权限 0600。
  • 继承时，项目级设置只在项目受信任时参与；显式档位必须是模型支持的档位。档位为 off 时 maxTokens 为 1024，否则取模型上限和 16384 中的较小值。

代价：额度与外发文本

命名和预览都额外消耗命名模型的额度，这部分消耗不计入 Pi 自带的会话用量统计。发送的对话文本可能包含业务信息。 和下一章对照：原位思考强度要先等分类器，最多 15 秒；自动命名在后台跑，用户不用等。

  • 命名请求使用新的随机 sessionId，cacheRetention 为 none，不带工具；认证、请求头、API 端点 baseUrl 和环境变量复用 Pi 为该模型解析的结果。

菜单：/personal → 自动会话命名

在 /personal → 自动会话命名 里选「查看状态」，可以看到状态、模型和思考强度。

  • 「选择命名模型」「选择命名思考强度」会先取消进行中的命名请求。
  • 菜单项调用功能内部注册的 auto-name 处理函数，参数见下表。这个处理函数只存在入口的 commands 表里，不是斜杠命令。

原位思考强度：按消息选档位

按每条新用户消息调整 GPT-6 Codex、Anthropic 协议分支的指定 Claude 模型或 Antigravity 分支的指定 Claude 模型的思考档位。三个分支分别用 configuration_update、Anthropic 原生逐消息标记或插件 runtime ID 路由写入档位。

功能 ID
inline-effort
入口
/personal → 原位思考强度（Jev / d1-ultra）
配置
默认 ~/.pi/agent/inline-effort.json，目录跟随 PI_CODING_AGENT_DIR；兼容读取旧的 jev-inline-effort.json
分类器
Jev（默认）· d1-ultra

什么时候分类

不同的消息需要的思考强度不同。这项功能给每条新用户消息自动选一个档位，结果叫决策。档位是思考强度的取值，分类器从 low、medium、high、xhigh、max 五档里选。 GPT-6 Codex、Anthropic 协议分支的三个指定 Claude 模型，或 Antigravity 分支的两个指定 Claude 模型才适用，thinking 不能是 off。Anthropic 协议分支还要求接口是 anthropic-messages，compat.supportsMidConvoEffort 为 true。Antigravity 分支要求 provider 是 antigravity，接口是 antigravity-api。不适用就不分类。 空白输入不调用分类器，沿用当前强度。当前强度是当前分支最近一次决策；没有决策就用基线，也就是 Pi 的 thinking 设置。 非空才调用分类器，最多等 15 秒。

分类结果怎么用

分类正常完成、档位有效，且概率是 0.5 到 1 之间的有限数，这叫结果合格。结果合格，扩展就采用这个档位。 超时、出错或响应无法解析时，扩展沿用当前强度并警告。结果不合格时也沿用，但不警告。 两种情况都写入决策；用户取消时不写。 多条新消息只分类一次，结果写给每一条。

Codex：为什么不改顶层参数

对 GPT-6 Codex，Pi 每次请求前，都按当前上下文构造完整的 input 列表。基线写在请求顶层的 reasoning.effort 字段。 新请求开头里和上一次请求相同的部分，叫缓存前缀。服务端复用缓存前缀的机制叫 prompt cache。README 的设计目标是保留缓存前缀，让 prompt cache 生效。 如果直接改 Codex 顶层，请求 2 从顶层字段起就和请求 1 不同。Pi 的 WebSocket 增量续传也要求 input 和 previous_response_id 以外的字段不变，否则发送完整 input。

按接入分支写入档位

对 GPT-6 Codex，扩展让顶层保持基线，在当前用户消息前插入一个 configuration_update 项，只写新档位。档位写在 input 里这条消息的位置上，这就是「原位」。 决策按消息时间戳存在会话里。模型、基线和已有上下文不变时，下一次请求重放同样档位，开头逐项不变。 Codex 档位和当前强度相同时，扩展不插入。档位回到基线时，扩展也要插入一项，抵消之前那一项。 Anthropic 协议分支使用 Pi 原生标记。扩展只修改 Pi 已生成的末尾空 system 消息里的 output_config.effort。顶层 output_config、thinking 和历史消息不变。message_end 保存实际发送的 providerThinkingLevel，供 Pi 重放历史标记。主会话 thinking 基线不变。 同一 Anthropic 协议请求由提供方内部重建或重试时，扩展复用原模型快照。流式期间切换模型后，旧回复仍保存实际档位。扩展不干预 Pi 的 max_tokens: 1 缓存预热回放。当前没有请求 ID 可用于区分请求，因此 max_tokens: 1 的主请求也不自动调整；等待 Pi 暴露请求 ID 后再区分。 Antigravity 是独立分支，不使用 Anthropic 消息级 output_config。插件不触发 onPayload，所以扩展在 context_with_system 分类后临时包装原生 streamSimple。扩展只改匹配当前 session、末条消息 timestamp 和模型的主请求 options.reasoning，交给插件按 -low、-medium、-high runtime ID 路由。max 和 xhigh 夹到 high，会话 thinking 和历史上下文不变。 Antigravity 的 message_end 保存实际 providerThinkingLevel。工具续调、重试和恢复沿用原决策。maxTokens: 1 预热和辅助 session 不干预。退出只恢复原 streamSimple，保留第三方后来的部分更新，也不覆盖第三方替换的新流。

决策跟随会话分支

决策是会话里的自定义条目，不发给模型。扩展只读当前分支路径上的决策，所以恢复会话、fork 或树导航后，旧消息保持原档位，不重新分类。 从 A1 另开分支 b 时，扩展仍继承共同祖先 U1 的决策，但读不到分叉后 U2 的决策。U3 是新消息，重新分类。 压缩后，压缩摘要承接被压缩部分的最后一次决策，强度不回落到基线。

状态栏

状态栏的 🧠 段显示当前强度、基线和最近一次决策的分类器，例如 🧠 xhigh · 基线 medium · Jev。当前强度等于基线时，只显示一个档位。 对 Codex，插入前，扩展核对 input 里 role 为 user 的项数。项数和本次上下文不一致时，扩展不插入，状态栏显示「未调整」。

在 /personal 里管理

在 /personal 里选原位思考强度，再选「查看分类模型与状态」。它显示三项：是否适用、后续用哪个分类器、当前分支最近一次决策。 通过「选择分类模型」打开选择器，选择后保存到全局配置，从下一条未分类的消息生效。其他会话和子代理的后续分类也读取这份配置。 「测试分类模型可用性」用固定样例测试分类器，不写决策。Pi 运行 agent 时，选择和测试都不可用。 功能 ID 从 jev-inline-effort 改为 inline-effort。旧的开关和配置文件仍能读取，保存时只写新文件；会话里的决策条目沿用旧类型名，旧会话可以直接恢复。

子代理与代价

子代理要加载本扩展才会分类，基线取子代理自己的 thinking 设置。外部 CLI 代理不经过本扩展。 代价有三项：每条新消息多等一次分类；分类消耗 OpenRouter 的额度；发出的文本可能含业务信息。d1-ultra 是付费模型。

安装、配置与升级

怎样安装和开发这个包，五个配置文件放在哪里，升级 Pi 后检查什么。

运行要求
Pi ≥ 1.0.1，Node.js ≥ 22.19.0
默认配置目录
~/.pi/agent/
环境变量
PI_CODING_AGENT_DIR

安装与开发

在仓库根目录依次执行三条命令：安装依赖，运行 npm run check，再用 pi install 安装这个仓库目录。 开发时循环三步：改代码，跑 npm run check，在 Pi 里执行 /reload。 

# 依赖走 npmmirror 镜像，不运行依赖的安装脚本
npm install --ignore-scripts \
  --registry=https://registry.npmmirror.com
npm run check
pi install "$(pwd)"

# 需要时对照官方源确认最新版本
npm view <包名> version \
  --registry=https://registry.npmjs.org
  • npmmirror 由 cnpm 团队维护（原淘宝 npm 镜像），同步有延迟。
  • npm run check 先做类型检查，再跑全部测试。卸载用 pi remove "$(pwd)"。
  • 这个包是 private 包，不发布到 npm，用本地路径安装。

五个配置文件

五个配置文件默认都在 ~/.pi/agent/。 设置环境变量 PI_CODING_AGENT_DIR 后，五个文件都改放在它指定的目录。

  • 五个文件的路径都由 Pi 的 getAgentDir() 决定。
  • 分类器设置从旧名 jev-inline-effort.json 改为 inline-effort.json。新文件不存在时才读旧文件；旧文件不删除、不改写，保存只写新文件。
  • clickable-paths.json 直接覆盖写入、失败不报错；其余四个先写临时文件再 rename。命名和分类器设置不改 Pi 的 settings.json。

升级 Pi 之后

升级 Pi 后，先把开发依赖升到和新 Pi 相同的版本。 再跑通 npm run check。边框测试加载 node_modules 里真实的 Pi 组件，所以新版 Pi 改了这个组件时，测试可能先报错。 最后在 Pi 里发一条消息，确认边框正常显示。

  • 原因见第 3 章：用户消息橙色线框替换了 UserMessageComponent.prototype.render，只在 TUI 模式下替换。会话关闭时停用这一层包装；如果当前 render 仍是这一层，就恢复原始方法。
  • 宽度小于 8 列，或原始渲染结果没通过行结构检查时，扩展直接返回原始渲染，不画边框。原始 render 抛错时没有兜底。
